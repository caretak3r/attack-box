# Host shipper design — required threat-model corrections

1. **Checkpoint only after remote acknowledgement, not after a local queue handoff.**
   - **Sections:** host-shipper-design §6 (“Data path”, “Drain loop”), §10(a), §11 steps 3–5, §16; `internal/telemetry/newrelic.go` (`Emit`, `record`, `Close`).
   - **Concrete failure:** proposed `TryEmit == true` means only that chunks entered `n.queue`. Advancing `state.json` at that point loses records if the shipper crashes, or `nr.Close` times out, before New Relic accepts them. `Count`/`Gauge` similarly only mutate `n.series`; advancing past those records loses them if the process exits before a metric flush.
   - **Correction:** replace the outbox handoff with per-record delivery receipts tied to successful log/metric batch submission. Persist the checkpoint only for a contiguous acknowledged prefix. Leave uncertain outcomes uncheckpointed for the recovery policy in finding 8. Shutdown must never advance the cursor for records merely present in `n.queue` or `n.series`.

2. **Make segment and checkpoint commits crash-durable, and specify torn-write recovery.**
   - **Sections:** §6 (“Disk queue”, “Startup”), §11 step 3, §15 queue tests.
   - **Concrete failure:** the buffered segment writer can lose already-read socket data on process exit. With no `fsync`, power loss can also persist a checkpoint without its segment bytes; the exposure is not bounded to one checkpoint batch. A corrupt checkpoint currently triggers replay of everything, including non-idempotent metrics.
   - **Correction:** use one disk writer and group commits: append a bounded batch, flush and `fsync` the segment before reading/admitting more, then let socket backpressure bound pending input. `fsync` each checkpoint temp file before rename and `fsync` the directory after checkpoint rename and segment creation/deletion. Use length, monotonic disk sequence, JSON length, and CRC32c framing on disk; truncate only a proven incomplete tail and quarantine mid-segment corruption. Validate that the checkpoint names the expected regular segment, has a nonnegative in-range offset, and lands on a frame boundary. Replace “corrupt state means replay oldest” with an explicit uncertain-recovery path; it is not generally deduplicable.

3. **Serialize rotation, read-ahead, overflow, and cursor changes; stop using wall time as segment order.**
   - **Sections:** §6 (“Segments”, “Bound”, “Drain loop”), §12 backpressure table.
   - **Concrete failure:** identical or backwards `UnixNano` names can collide or reorder replay. More seriously, overflow can delete a segment while the drain loop is retrying a record read from it. The overflow path and drain path can then advance different cursors, causing a skip or cursor regression.
   - **Correction:** name segments with a persisted, monotonically increasing `uint64` sequence and create them exclusively. Have exactly one queue owner—or one lock covering append, size accounting, roll, read-ahead, acknowledgement, and checkpoint update—with monotonically increasing checkpoint generations. Never delete the active append segment, the checkpoint segment, or any segment containing read-ahead/unacknowledged records. On exhaustion, apply finding 9’s admission policy rather than independently moving the delivery cursor. Enforce the byte cap against `current_bytes + buffered_bytes + incoming_bytes`, looping as needed, and reject a record that can never fit an empty queue.

4. **Authenticate the peer once and derive an immutable producer role from it.**
   - **Sections:** §3–4, §7 source assignment, §8 bait liveness, §9 adapters.
   - **Concrete failure:** filesystem group permission authorizes `connect`, but it does not identify which producer sent a record. A bait can make its first record `runtime` and acquire that source, then send any later stream. Any adapter or extra connection can also keep a global `bait_connected` value true. Arbitrary boot IDs create an unbounded per-boot sequence/gap map.
   - **Correction:** read and verify `SO_PEERCRED` immediately after `accept`, fail closed on an unexpected uid/gid, and pin the connection to one role. Falco and the nft adapter both run as root, so use separate sockets or dedicated service uids if they must be distinguished. Set `source` only from that verified role, never from the first record or a client flag. Enforce a role matrix: bait → `edge`/`transcript`/`probe` plus `bait_heartbeat` and allowlisted metrics; runtime → `runtime`/`falco`; egress → `egress`/`egress_blocked`. Count only verified bait-role connections in bait liveness. Require canonical `<16 hex>-<decimal seq>` IDs, one boot per connection, and a small expiring sequence cache keyed by authenticated producer; do not retain attacker-selected boots without bound. Treat gap reports as advisory, not proof of drops by a hostile producer.

5. **Specify the actual one-way socket invariant and add connection/ingress exhaustion controls.**
   - **Sections:** §3 socket claims, §7 line/connection rules, §12 mount table.
   - **Concrete failure:** mode `0220` does not turn `SOCK_STREAM` into a read-only or write-only channel; after `connect`, it remains full duplex. Separately, eight idle or slow clients can occupy every slot and prevent Falco/egress delivery, while unlimited valid traffic can consume parser and disk bandwidth.
   - **Correction:** state the invariant narrowly: the socket filesystem mode authorizes connection, historical files are unreachable, and the application protocol sends no bytes to producers. On accepted sockets, disable the shipper’s write side and never add errors, acknowledgements, or other responses; retain the read-only bind mount rather than assuming an rw fallback is equivalent. Add idle and total-per-line read deadlines, per-role connection limits with slots reserved for runtime and egress, and global/per-role ingress byte-rate limits before JSON parsing and disk append. Close or shed the abusive role without consuming another role’s slots.

6. **Bound the complete decoded record and its post-chunk output, and make memory queues byte-bounded.**
   - **Sections:** §4 record shape, §5 `QueueSize`/`MaxRecord`, §7 attribute checks, §10(a), §12–13 sizing and `MemoryMax`.
   - **Concrete failure:** top-level string truncation does not constrain nested `Attrs`, `TaskLabels`, or fixed fields such as `UserAgent`, `Action`, and `Resource`. Chunking repeats attributes in every chunk, so a near-2-MiB record can expand into hundreds of megabytes. Ten thousand such records in `Spool`, or twenty thousand in the New Relic queue, also exceed the proposed 256-MiB service limit by orders of magnitude.
   - **Correction:** reject invalid UTF-8 and impose recursive depth, total-node, array-length, key-count, and aggregate-string limits on all attributes, including the adapter’s nested `event` object. Cap every fixed string and `TaskLabels`, and set an explicit body-byte cap compatible with the 128-KiB application limit. After sanitization and source/ID addition, run the real chunk/log-item sizing logic before disk admission: every generated item must fit the New Relic payload envelope and total expanded bytes must have a hard ceiling. Define whether line limits include the newline and make producer/consumer limits consistent. Add byte semaphores covering channel plus in-flight records in both spool and shipper/New Relic queues; validate those budgets, client read buffers, and runtime headroom against `MemoryMax`.

7. **Replace attacker-resettable metric-name caps with a fixed contract.**
   - **Sections:** §4 `MetricRecord`, §6 metric drain, §7 `Metric.Name`/`Metric.Value`; implementation_plan “Metrics”.
   - **Concrete failure:** a producer can reconnect or choose a new boot ID to reset the “64 distinct names per producer run” allowance. The existing 2,000-series cap does not repair this: `flushMetrics` empties `n.series`, so churn resumes after every flush and can consume ingest quota or crowd out legitimate series.
   - **Correction:** allow only the exact metric names required by implementation_plan plus an enumerated shipper set, and permit metrics only from the expected role. Require `Kind` to be exactly `count` or `gauge`, require finite values during admission, and reject unknown kinds instead of relying on downstream behavior. Apply global and per-role metric rates independent of connection, boot ID, or flush generation. Keep `SafeLabels` as the label whitelist; do not add replay IDs to metric labels.

8. **Define chunk-safe log deduplication and a separate, honest metric replay policy.**
   - **Sections:** §2 unchunked-event requirement, §4 ID, §6 startup/overflow, §7 `record_id`, §10(a), §15 round-trip test, §16 dedup; `internal/telemetry/event.go` (`Chunk`) and `sink.go` (`SafeLabels`).
   - **Concrete failure:** every chunk inherits the same `record_id`; collapsing solely on that ID discards all but one chunk and breaks body reassembly. Raw attacker IDs also collide across producers. Metrics have no equivalent protection: `SafeLabels` removes a replay ID and replayed `Count` calls add their values again.
   - **Correction:** namespace the validated producer sequence by verified role and boot. Define an event key from `(source, boot, seq, body_sha256)` and a chunk key from `(event key, chunk_index)`; every NRQL view/alert that deduplicates must preserve every distinct chunk index rather than use `uniqueCount(record_id)`. At admission require or normalize zero `BodySHA256`, `ChunkIndex`, and `ChunkCount` on the unchunked wire record so the spool cannot carry a false provenance claim. Keep final-hop `Chunk` as the sole creator of the full-body hash and chunk metadata. For uncertain checkpoint recovery, replay logs under those keys but suppress the ambiguous metric prefix and emit a current `metric_replay_gap`; this chooses possible metric loss over silent double counting. Do not claim `record_id` deduplicates metrics or add high-cardinality replay IDs to metric labels.

9. **Make overflow producer-isolated; a hostile bait must not erase host evidence.**
   - **Sections:** §6 “Bound”, §12 rotation/backpressure, §16 forensic backstop.
   - **Concrete failure:** global drop-oldest lets a valid-looking bait flood delete unconsumed Falco, egress, checkpoint, and earlier attack records. An overflow event emitted into the same full queue can disappear immediately. The bait can likewise flood stdout until Docker’s 30-MiB rotation budget discards the supposed independent forensic history.
   - **Correction:** account queued bytes by verified role and reserve dedicated runtime/egress capacity within the global bound. When the bait share is full, reject/drop incoming bait records before disk; never delete unacknowledged host-role records to make room for bait. Record overflow in a root-owned local shipper log outside the spool and carry cumulative drop counts on the direct host heartbeat. Describe Docker stdout as a best-effort, bounded backstop, not reliable forensic retention. If that history is required, send it to the planned external write-only/object-locked archive rather than relying on attacker-driven rotation.

10. **Retain bait-side in-flight batches across reconnects and count them in the bound.**
    - **Sections:** §5 writer behavior, §12 backpressure, §15 reconnect/Close tests.
    - **Concrete failure:** records removed from the channel into the writer’s current batch or `bufio.Writer` are no longer queued when a write fails. Closing the connection and redialing without replaying that batch loses them even though the channel had room; counting only `Errors` does not reveal which records vanished.
    - **Correction:** keep the encoded current batch and stable producer IDs until a complete flush succeeds, then release it. On error, reconnect and resend that same batch before taking more records; a partial prior write may create duplicates, which finding 8 handles, but must not create a silent gap. Include in-flight bytes in finding 6’s queue budget. If `Close` reaches its deadline, return the error and account all unreleased records as dropped/lost rather than reporting a successful drain.

11. **Make heartbeat identity server-owned and narrow what liveness proves.**
    - **Sections:** §5 item 5, §7 source assignment, §8 heartbeat design and alerts, §16; implementation_plan “Alerts”; `internal/telemetry/newrelic.go` (`heartbeatLoop`).
    - **Concrete failure:** the direct host heartbeat bypasses socket validation, while the proposed `HeartbeatAttrs` list does not add `source`. Thus the stated `source=shipper` alert has no guaranteed matching events. Conversely, unscoped socket records can refresh bait liveness, and a compromised producer can keep sending syntactically valid heartbeats.
    - **Correction:** construct `source=shipper`, a reserved host action, and a host-liveness version inside `heartbeatLoop` or other trusted shipper code; never accept that identity from a socket record. Permit only `source=bait`, `action=bait_heartbeat` from a verified bait-role connection, and compute `bait_connected`/`last_bait_record_age_ms` exclusively from that role. Define these fields as “a bait-role socket is connected/sending,” not proof that the original process is healthy or uncompromised. A host heartbeat can alert on shipper/egress absence, but must not be described as proving “host fine” or detecting a malicious host.

12. **Close filesystem and configuration ownership holes explicitly.**
    - **Sections:** §6 queue/state files, §12 ownership and unit hardening, §13 shipper configuration.
    - **Concrete failure:** `abx-ship:abx-ship 0600` makes the license-bearing env file writable by the service uid outside the unit’s read-only mount namespace; that uid can then kill its process to obtain a restart. The design also relies on directory modes without explicitly setting `StateDirectoryMode` or specifying no-follow/exclusive file operations, so a miscreated/writable queue path can turn predictable segment/state names into symlink clobber targets.
    - **Correction:** make the env file and unit/binary root-owned (`root:root 0600` for the env file); systemd can read it before dropping uid. Set `StateDirectoryMode=0700` and verify owner, mode, and non-symlink directory type at startup. Open the queue directory once and use dirfd-relative no-follow operations; create segments exclusively, create checkpoint temps with random `O_EXCL` names and mode `0600`, and verify regular files by `fstat`. Do not chmod, truncate, rename over, or unlink a path reached through an unverified symlink or a group/world-writable parent. Treat NR endpoint configuration as root-only and enforce the New Relic destination restriction in the host/provider egress rules, not only with a uid match.

13. **Narrow the threat-model claim and state the shipper-compromise blast radius.**
    - **Sections:** §3 process boundary/firewall, §8 heartbeat trust, §12 env/firewall, §16 residual risk; implementation_plan “Threat model”, “Secrets on the decoy VPS”, and “Remaining risk”.
    - **Concrete failure:** the plan assumes root on the VPS, but host root can read the shipper key, alter spool/checkpoint files, impersonate any socket role, bypass uid-based nft rules, and post forged heartbeats. Compromise of only `abx-ship` still exposes the ingest key and permits arbitrary telemetry within its egress reach. A dedicated New Relic account limits the key to ingest/quota abuse; it does not satisfy a literal requirement that host-root attackers get nothing that reaches Rohit.
    - **Correction:** state that this shipper protects against compromise of the container/sandbox, not host root. Declare host-root or `abx-ship` compromise a loss of telemetry confidentiality, integrity, availability, and the ingest key, with revocation, provider-console power-off, and rebuild handled outside the decoy. Do not use any positive heartbeat generated on that host as compromise evidence. Keep the dedicated ingest-only account and absence alerts as damage reduction. If host-root telemetry integrity remains a hard requirement, this host-resident architecture cannot meet it without an independent trust/liveness anchor; say so instead of claiming the socket or firewall provides it.
